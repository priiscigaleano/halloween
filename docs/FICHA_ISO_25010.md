# Ficha de Autoevaluación de Calidad ISO/IEC 25010 — Concurso de Disfraces de Halloween

| Característica ISO 25010 | Evidencia técnica en el código | Estado |
|---|---|---|
| 1. Adecuación Funcional | api/config/database.php crea la conexión con new PDO('mysql:...'). Los endpoints persisten en MySQL con prepared statements: register.php (INSERT usuarios), votar.php (INSERT votos + UPDATE disfraces en una transacción), disfraces/index.php (SELECT/INSERT), update.php y delete.php (borrado lógico). halloween.sql define claves foráneas y UNIQUE(id_usuario, id_disfraz). Corregido: el proyecto usaba mysqli y se migró a PDO. Corregido: el hash del admin en el SQL no correspondía a 'admin123'. | **Cumple** |
| 2. Eficiencia de Desempeño | El listado sale de una sola consulta (disfraces/index.php) y no incluye foto_blob. Antes, abrir cada expediente volvía a pedir toda la lista; ahora app.js usa la caché DISFRACES y solo la refresca tras votar. Respuestas JSON livianas. La latencia no se midió en este informe: verificarla en Chrome DevTools, pestaña Network. | **Cumple (falta medir en Network)** |
| 3. Compatibilidad | Frontend HTML/CSS/JS vanilla que solo habla con el backend mediante fetch() y JSON (carpeta api/); el backend PHP no genera HTML. Cada capa puede cambiarse sin tocar la otra. CORS limitado al origen propio. Se usan APIs estándar; si el navegador no soporta 'inert', el diálogo igual se cierra con Escape y devuelve el foco. | **Cumple** |
| 4. Fiabilidad | Todos los endpoints usan try/catch de PDOException con PDO::ERRMODE_EXCEPTION. Códigos HTTP: 200/201 éxito, 400 datos inválidos, 401 no autenticado, 403 sin permisos, 404 no existe, 405 método no permitido, 409 duplicado (usuario o voto repetido), 500 error interno. El voto usa transacción con rollBack(). El detalle técnico va a error_log, no al cliente (antes se mostraba el error de conexión). | **Cumple** |
| 5. Seguridad (OWASP) | BCRYPT: password_hash(..., PASSWORD_BCRYPT) en register.php y password_verify en login.php. SQLi: prepared statements PDO con EMULATE_PREPARES=false. XSS: textContent en mensajes y esc() en datos de la BD dentro de innerHTML (antes sin escapar en app.js, auth.js y admin.js). Sesión HttpOnly + SameSite=Lax y session_regenerate_id() al loguear. Subidas validadas por tipo MIME real (finfo) y tamaño (2 MB). CORS ya no refleja cualquier origen. Pendiente para producción: usuario root sin clave, contraseña admin123 por defecto, falta HTTPS, token CSRF y límite de intentos de login. | **Cumple (con observaciones)** |
| 6. Usabilidad / Accesibilidad | axe-core (WCAG 2.0/2.1 A y AA y buenas prácticas) sobre 5 vistas, con el modal abierto: 0 violaciones tras la refactorización. Contraste del rojo principal: 6.16:1. Teclado: skip link, button/a nativos, :focus-visible de 3 px, diálogo con foco inicial, fondo inert, cierre con Escape y retorno del foco, aria-live en todos los mensajes. Falta que el equipo ejecute y capture Lighthouse en Chrome: no pudo correrse en el entorno donde se hizo la refactorización. | **Cumple (confirmar Lighthouse 100/100)** |
| 7. Mantenibilidad | Capas separadas: api/config (conexión), api/helpers (sesión, CORS, fail()), api/auth, api/disfraces y api/votos; frontend en auth.js, app.js, admin.js, efectos.js y una hoja de estilos. fail() centraliza los errores.
